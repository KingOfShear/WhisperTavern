# DesireGrimoire 交互界面设计

> 定位：本文定义前端的**信息架构、核心界面与交互模式**，与 [technical-plan.md](./technical-plan.md) §5 各子系统一一对应。
> **文档层级（2026-09）**：本文是 [technical-design.md](./technical-design.md) 之下的 **UI 详细规格**；§2 信息架构与总设计 §30 一致。
> 用户熟悉 SillyTavern，布局习惯向其靠拢（降低迁移成本），但交互细节按本项目的差异化能力（缓存遥测、消息树、Agent 工作流）重新设计。

## 1. 设计原则

1. **缓存状态可见化**——这是本项目最大卖点，必须长在 UI 里而不是藏在日志里。分区颜色语义贯穿所有界面（Inspector、世界书编辑器、遥测面板用同一套色）。
2. **聊天工作台是常驻主界面**——卡/书/预设管理等全部以右侧面板或全屏抽屉呈现，不整页跳转，不打断心流。
3. **消息即树**——swipe/分支不是隐藏功能，每条消息上直接可见变体计数与导航。
4. **桌面优先**（1280px+ 为一等公民），窄屏把侧栏/面板折叠为抽屉；触屏适配放 P5。抽屉折叠机制从 P0 起按可触屏标准实现（边缘滑动零成本预留），移动端完整布局与手势设计仍属 P5，不提前承诺。
5. **生成过程透明可介入**——Agent 工作流的各阶段产物可查看、可编辑、可单独重跑。

## 2. 信息架构与全局布局

```
┌───────────┬────────────────────────────────┬───────────┐
│ 左侧栏     │         聊天主区                │ 右侧面板   │
│ (可折叠)   │                                │ (抽屉式,   │
│           │                                │  可折叠)   │
│ 角色卡库   │   消息流 (虚拟滚动)              │ · 世界书   │
│ 聊天会话树 │                                │ · 预设     │
│ (按角色分组)│   底部输入区                    │ · 工作流   │
│           │                                │ · 遥测     │
│ ＋新聊天   │                                │ · 设置入口 │
└───────────┴────────────────────────────────┴───────────┘
```

- 左侧栏上半为**角色卡库**（卡片网格/列表切换，头像+简介），下半为当前角色的**会话列表**；点击会话 = 载入消息树当前指针所在分支。
- 右侧面板为多标签页（世界书 / 预设 / 工作流 / 遥测），对应"当前会话正在用的"实例，点开即改、即存、即生效于下一轮。
- 顶栏：当前角色名 + 会话名 + 上下文用量环形图（`已用/预算`）+ 缓存命中徽标（绿=稳态命中 / 橙=上轮失效 / 红=前缀断裂）。

## 4. 核心界面详设

### 4.1 聊天工作台（单聊）

```
┌─────────────────────────────────────────────────┐
│ 🐱 小猫之神 · 会话「酒馆之夜」   ◔ 38k/128k  🟢71% │
├─────────────────────────────────────────────────┤
│                                                  │
│ 👤 用户                                          │
│   我推门走进酒馆，环顾四周……                       │
│                                                  │
│ 🐱 小猫之神                              #4 ◀ 2/3 ▶│
│   (正文渲染 markdown / details 折叠思维 / 代码块HTML)│
│   ┌─────────────────────────────────────┐        │
│   │ ✏️编辑 🔁重roll 🧬分支 📋复制 🗑删除 💾pin │ hover │
│   └─────────────────────────────────────┘        │
│                                                  │
├─────────────────────────────────────────────────┤
│ [输入框 (Shift+Enter 换行)          ] [发送 ▾]    │
│  发送▾菜单: 普通生成 / 续写 / 代入(user视角) / 触发工作流│
└─────────────────────────────────────────────────┘
```

- **变体导航 `◀ 2/3 ▶`**：一条消息上同时呈现 swipe 数与分支数；`＋` 新建变体。点开有树形缩略图（时间旅行分支视图）。
- **pin（固定）**：把某条消息钉住为"永远注入"，实际上是把该消息复制进 header 区（缓存友好，进稳定前缀）。
- **`/` 词条快检（P1/P2，2026-09 补）**：输入框键入 `/` 唤出微型词条浮层——模糊搜索当前激活的世界书条目，选中即插入 `@D` 引用或纯文本；浮层内只读浏览，改设定仍走右侧抽屉。目标：宏大世界观频繁查设定时不必离开输入框、不打断心流。
- 生成中：消息气泡内流式渲染；工具条变为「⏹停止 / 🔄重roll」。
- 思维链（reasoning 模型）默认折叠为 `<details>`，可展开。

### 4.5 Prompt Inspector（P1/P2）

```
┌─ Prompt Inspector · 第42轮 ───────────────────────┐
│ 总 38,204 tok · 缓存命中 71% · 上轮失效 480 tok 🟢 │
│ ┌───────────────────────────────────────────────┐ │
│ │ 🟩 系统提示+角色卡      header    1,204 tok 稳定│ │
│ │ 🟦 前置世界书(已毕业)   stableWB   6,830 tok 稳定│ │
│ │ 🟧 新增世界书(1条)      freshWB     412 tok 本轮│ │
│ │ 🟪 剧情摘要链 S1..S5   summary   2,100 tok 追加│ │
│ │ ⬜ 对话历史 #1-#41     history  27,000 tok 追加│ │
│ │ 🟨 深度注入@D4         injection   180 tok     │ │
│ │ 🟥 风格指令/挥发宏     tail        480 tok 易变│ │
│ └───────────────────────────────────────────────┘ │
│ [▸展开任一区: 查看/复制最终发送文本]                │
│ [与上一轮diff ▾]  [🔍缓存二分: 定位首个分歧字节]    │
└───────────────────────────────────────────────────┘
```

- 每区显示 token 数与**稳定性徽标**（稳定/追加/本轮/易变）。
- 缓存二分（**两级形态**，2026-09 定稿）：
  1. **第一层：段级哈希对齐条带**——两轮 prompt 按段哈希左右两列对齐排布（绿 = 哈希一致 / 红 = 分歧），第一处红块即首个分歧段，无需读文本；
  2. **第二层：点击红块下钻分屏字节级 diff**——左第 k 轮 / 右第 k+1 轮逐段垂直对齐，分歧段高亮并注明原因（改动的宏 / 移动的条目 / 被编辑的消息 / 新毕业条目）。
- 形态依据：二分是**对齐诊断**而非改动审阅——分屏沿中缝扫视定位错位最快，内联红绿适合稀疏修改的审阅场景。因此：Inspector 面板内的快速对比（「与上一轮 diff ▾」）用**内联红绿**（窄容器放不下分屏）；二分工具**全屏覆盖层**展开用**分屏**。

### 4.7 Agent 工作流面板（P4）

```
┌─ 工作流 ─────────────────────────────────────────┐
│ ①大纲(快模型) ─→ ②正文(主力) ─→ ③润色(低温度)     │
│ [✓ 1.2s/3k tok] [●流式中…] [等待]                 │
│ ▸ 大纲产物 (可编辑 → 重跑后续阶段)                 │
│ ▸ 正文草稿 (diff 视图 vs 润色稿)                   │
│ 记忆: [摘要链S6生成中…] [实体档案: 酒馆/盗贼 ✓]     │
│ 共享 header 缓存: ✓ 三阶段共用一份 (省 ~68%输入)    │
└───────────────────────────────────────────────────┘
```

- 阶段展示用**横向节点卡片流**（可横向滚动，2026-09 升级）：每节点一张卡（状态/耗时/token），点击侧滑出对应产物与记忆档案比对；失败可从该阶段重跑。
- **DAG 约束**：串行段横向排布；**并行节点必须分泳道**（同层并行卡片纵向成行），不许把 DAG 压成单线——Workflow 本身支持并行（agent-runtime-spec），线性展示会在 P4 返工。
- 记忆区：摘要链浏览（每块覆盖的消息区间）、实体档案卡（Scribe 维护的事实）。

### 4.9 人工批准卡片（P3）

- 危险工具或工作流节点触发 `approval.requested` → 聊天流内插入卡片：动作名、风险等级（low/medium/high）、申请的权限清单、批准/拒绝、过期时间（agent-runtime-spec §114–§116）。
- **等待态必须可关窗**：批准请求持久化在 `approvals` 表，重启后仍在；批准后靠事件唤醒 Run 继续，不依赖内存 Promise。
- 过期按 policy 处理（视为 rejected 或延长等待），不允许无限悬挂。

**【2026-09 补】四值结果语义与 fail-closed**（对齐 agent-runtime-spec §115.1）：

| outcome | 卡片表现 | Run 后续 |
|---|---|---|
| `allowed_once` | 「已批准」，**只放行被问到的那一个动作** | 继续 |
| `rejected` | 「已拒绝」 | 该次工具调用落 `denied`，Run 继续（模型看到拒绝结果后可自行恢复） |
| `cancelled` | 「已撤回」 | 随 Run 取消流程 |
| `unavailable` | **「无可用审批者，已自动拒绝」** | 落 `denied`，Run 继续 |

UI 规则：

- **UI 只是回答者之一，不是唯一通道**。后台 workflow / 定时任务 / 群聊跑批**没有 UI 回答者**，此时一律落 `unavailable` 并自动拒绝——绝不能默认放行，也绝不能让 Run 永久挂在 `waiting`。卡片上要如实显示这个结果，**不要假装"等待中"**。
- **卡片不重复渲染工具入参**。入参已随 `tool.call.started` 流式下发，卡片通过 `toolCallId` 挂到那张工具卡片上，只额外显示「为什么问」（`reason`）。两份入参副本必然漂移。
- **审批结果不进模型转录**。`approval.requested` / `approval.decided` 是 log-only 审计对，模型看到的只是推导出的工具结果。
- 未配对的 `approval.requested`（有问无答）要能被识别为异常态并显式提示，不能静默消失。
- per-chat 策略（`ask` / `never`）在设置里可切；`never` 下所有请求确定性拒绝且不派发任何回答者，UI 应直接标注该 chat 处于"无人值守"策略。

**【2026-09 补】审批入口分流：inline 卡片 vs 通知中心**：

- **当前 chat 的审批**：仍 inline 插入聊天流卡片——人在场，直接决策最高效，不打折展示。
- **跨 chat / 后台 workflow 的审批请求**：进**顶栏通知中心**（未读徽标 + 过期倒计时 + 点击跳转到对应会话/Run）。通知中心是 UI 回答者通道的延伸，**不改变 fail-closed 语义**：过期或无应答仍按 policy 落 `rejected` / `unavailable`，绝不默认放行。
- 通知中心内的审批项与 inline 卡片**同构**：同样显示四值结果与"为什么问"（`reason`）；全局通知不可默认静音——静音等于变相 `unavailable`。

### 4.10 分支血缘提示（P3）

- 从 `chat_branches` 的 `fork_message_id` / `seed_length` / `is_seeded` 读出血缘（database-schema §21）。
- 分叉出去的分支在消息流里标出「继承前缀」区间，并在缓存诊断里显示**这段是否命中了父分支的缓存前缀**。
- 父分支那一段若发生编辑或条目退役，继承前缀随之失效——失效沿血缘传播，UI 要能解释"为什么这个新分支第一轮就没命中缓存"。

## 5. 设计系统与分区色彩语义

**一套 zone 颜色贯穿全局**（Inspector / 世界书编辑器 / 遥测 / 工作流通用）：

| Zone | 色 | 语义 |
|---|---|---|
| header | 🟩 绿 | 逐字节稳定 |
| stableWB | 🟦 蓝 | 已毕业，追加式 |
| freshWB | 🟧 橙 | 本轮新增 |
| summary | 🟪 紫 | 冻结追加 |
| history | ⬜ 灰白 | 追加式 |
| injection | 🟨 黄 | 贴近末端 |
| tail | 🟥 红 | 每轮可变（缓存杀手出没区） |

- 基调：暗色主题为默认（RP 用户主流习惯），Tailwind + shadcn/ui，主色可与 zone 色系区分。
- **无障碍（P5 主题系统，2026-09 补）**：zone 色相语义不动（不换低饱和配色），但**纯色不得是唯一信息通道**——每个 zone 附带第二通道（角标图标 / 明度分层 / 微纹理），色弱用户靠第二通道也能区分七区（WCAG 1.4.1「不得仅用颜色传达信息」）。
- 排版：消息正文 15-16px、行高 1.7；长文阅读宽度上限 ~72ch。
- 长会话性能：消息流虚拟滚动（react-virtuoso 类方案），万条消息不卡。

## 6. 前端架构（apps/web）

- **路由极简**：`/`（工作台）为唯一主路由；管理功能均为工作台内面板/抽屉；`/settings` 独立页。
- **状态（Zustand）**：`chatStore`（会话列表+当前消息树+指针）、`promptStore`（编译快照、分区结果、Inspector 数据）、`workflowStore`（阶段状态）、`settingsStore`（模型/密钥/偏好）。
- **实时通道**：单一 SSE 连接复用所有事件——`message.delta`（流式 token）、`workflow.stage_started` / `workflow.stage_completed`（工作流阶段）、`usage.recorded`（遥测入库即推）、`cache.invalidated`、`agent.run.*` / `tool.call.*`、`approval.requested`。断线自动重连+按消息号补齐。
  **事件名以总设计 §5.4 的权威清单为准（点分记法）**；早期稿中的冒号记法（`message:delta` / `stage:update` / `usage:record`）作废。
- **编译在服务端，展示在前端**：前端永远只消费编译快照（含分区、token、哈希链），不在前端二次拼 prompt——保证"所见即所发"。
